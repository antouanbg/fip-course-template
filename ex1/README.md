## Как работим

**Сами.** Асистентът задава задачите и проверява резултата — не показва решението. Ред за помощ, когато сте блокирали:
**1.** това README и „Готово, когато" → **2.** подсказката под задачата (отворете я едва след 5 мин опити) → **3.** агентът (само в Част B) → **4.** съседът → **5.** асистентът — с конкретен въпрос („при X очаквам Y, получавам Z"), не „не работи".

## Цел

- Да видите нагледно **frontend / backend / база данни** и как браузърът говори с отдалечен сървър по HTTP.
- Да четете JSON отговор и да го показвате с JavaScript; да различавате HTTP грешка от мрежова грешка.
- Да работите с агент **като reviewer**: формулирате задача → получавате код → проверявате го на контролна точка → можете да го обясните.

## Какво има в кода

`index.html`: бутонът **Get Joke** прави `fetch()` (HTTP GET) към `https://api.chucknorris.io/jokes/random`, получава JSON и показва полето `value`.

| Слой | Тук | Роля |
|---|---|---|
| **Frontend** | `index.html` в браузъра ви | UI + логика на клиента |
| **Backend** | `api.chucknorris.io` | Отговаря на HTTP заявки с JSON |
| **Database** | зад API-то, невидима за нас | Съхранява данните |

## Част B · С агент (40 мин) — всяка задача = запис в `AGENT_LOG.md`

- [ ] **B1 Обясни.** Поискайте обяснение на `<script>` ред по ред. После **със свои думи**, в коментар в кода (3–4 изречения): какво връща `fetch()`, защо има два `await`, какво се случва при клик.
  **Готово, когато:** можете да отговорите без да гледате: „какво е `data`, ако махна втория `await`?"
- [ ] **B2 Обработка на грешки.** Поискайте `try/catch` + проверка на `response.ok` + съобщение за потребителя (клас `.error`). **Контролна точка — преди да приемете кода** тествайте трите сценария и попълнете таблицата в края:
  1. грешен path (`/jokes/randomXYZ`) → какъв status? влиза ли се в `catch`?
  2. грешен домейн (`api.chucknorris.invalid`) → какво хвърля `fetch`?
  3. DevTools → Network → **Offline** → какво вижда потребителят?
  **Готово, когато:** и трите сценария показват съобщение в страницата (не само в конзолата) и таблицата B2 е попълнена.
- [ ] **B3 UX.** Докато заявката тече: бутонът е `disabled`, текст „Loading…". След отговор: шегата се добавя в `<ul id="history">` с последните 5, най-новата отгоре. `finally` връща бутона.
  **Готово, когато:** 6 клика → в списъка са 5; след грешка бутонът пак е активен.
- [ ] **B4 Търсене.** Поле + бутон **Search** → `…/jokes/search?query=<текст>`. Отговор: `{ total, result: [...] }`. Покажете `total` и списък. Обработете празен вход, `total = 0`, специални символи (`encodeURIComponent`). API-то връща **400** при под 3 символа — проверете го сами.
  **Готово, когато:** `computer` показва брой + списък; `zzzz` показва „няма резултати"; `c++` не чупи заявката.

**Преди да приемете код от агента** — чеклистът в [PROMPTS.md](PROMPTS.md): работи ли? прави ли *само* поисканото? без библиотеки? тествахте ли грешния път? можете ли да обясните всеки ред?

<details><summary>Подсказка B2</summary>

`fetch` **не хвърля** при 404 — Promise-ът се resolve-ва с `response.ok === false`. Хвърля (`TypeError: Failed to fetch`) само при мрежова грешка. Ако агентът ви е дал само `try/catch`, тествайте сценарий 1 и вижте какво липсва. Готовите prompt-ове са в `PROMPTS.md`, раздел 3.
</details>

<details><summary>Подсказка B3</summary>

`finally` се изпълнява и при успех, и при грешка — там е мястото за `btn.disabled = false`. За „най-новата отгоре": `ul.prepend(li)`; за ограничението: `while (ul.children.length > 5) ul.lastElementChild.remove()`.
</details>
